# JupyterHub (z2jh) front door on local kind

*2026-10-01 · zero-to-jupyterhub chart **4.4.2** (latest stable, JupyterHub 5.5.2, KubeSpawner 7.1.0; tgz sha256 `0ddfa517…3c3e`) · kind v0.32.0 (node v1.36.1, kindnet), helm v4.1.4, ingress-nginx as on "labs" · Docker Desktop, arm64 Mac · branch `spike/per-user-stacks` · reproducible with `spike/hub/deploy.sh` then `spike/checks/frontdoor-hub/run.sh`*

This is option 3 from the scoping plan, timeboxed as the skeptic asked. The participant pod is the same as `spike/chart`'s:
- The Lab is the singleuser container, from image `eoapi-spike-hub-lab` (the spike Lab image plus `jupyterhub==5.5.2`).
- Postgres runs as a native sidecar (`singleuser.initContainers`, `restartPolicy: Always`).
- The other 7 services run as `singleuser.extraContainers`.

z2jh replaces our participant loop, Ingress, NetworkPolicy and pre-puller. Release `hub`, namespace `spike-hub`, on the same kind cluster as `spike-own`, which is left untouched.

Files: `spike/hub/values.yaml`, `spike/hub/Dockerfile`, `spike/hub/jupyter_server_config.py`, `spike/hub/deploy.sh`, `spike/checks/frontdoor-hub/{run.sh,hub.py,browser.py}`. Screenshots: `evidence/screens/frontdoor-hub-0[1-5]-*.png`.

## Results

`checks/frontdoor-hub/run.sh`, final run (run 3): **64 PASS, 1 FAIL, 0 BLOCKED**.
- The FAIL is a design finding (finding 1), not broken wiring.
- Run 2 had 62 PASS / 2 FAIL. The second FAIL was a check bug: it counted STAC Browser's known `OPTIONS` 405 (see below), and is fixed.
- Run 1 had empty NetworkPolicy probes (`kubectl exec` without `-i`), a 403 on `/api/status` (an API path doesn't start the OAuth hop), and a Chromium that ignored the secure-origin flag. All three were check bugs, fixed before run 2.
- Raw logs (gitignored): `evidence/.frontdoor-hub-{deploy1,deploy2,run1,run2,run3}.log`.

What works:

- **Login is per user, at one URL, against a Secret.**
  - The authenticator is a 9-line `Authenticator` in `hub.extraConfig`. It reads Secret `participant-passwords`, mounted on the hub: one key per user, `openssl rand -hex 6`, created once by `deploy.sh`. It compares with `hmac.compare_digest`. This is not SharedPassword or Dummy.
  - `allowed_users: [u01, u02]`.
  - A wrong password → 403. u01's password as `u02` → 403.
  - Anonymous requests to 7 paths under `/user/uNN/` reach only the hub login page, or 403. Nothing leaks.
- **Pre-spawn through the REST API works.** Service `spike-admin` has role scopes `admin:users, admin:servers`, but not `access:servers`, so it cannot open a Lab. Its token is generated by the chart into Secret `hub`. `POST /hub/api/users/uNN/server` → 202 for both users, and both pods reached 9/9 Ready.
- **`/user/uNN/{stac,raster,vector,oidc,browser,manager}/` work through the hub, and every generated URL carries the user's two-level prefix.**
  - stac `self=http://hub.spike.local:18080/user/u01/stac/`; tilejson `tiles[0]=…/user/u01/raster/…`; tipg `self=…/user/u01/vector/collections`.
  - The mock-oidc issuer, authorize and token endpoints are all under `…/user/u01/oidc`.
  - The stac-manager bundle is served from `…/user/u01/manager/client.*.js`.
  - Both stacks serve the baked data: glad, 100 items; ecoregions, 2548.
  - How it works: jupyter-server-proxy with `absolute_url` forwards `<base_url><prefix>`, so every root path becomes `/user/{username}/<prefix>` (`jupyter_server_config.py`, verified in `jupyter_server_proxy/handlers.py:_get_context_path`). KubeSpawner expands `{username}` in `extra_containers`, `init_containers` and env (`kubespawner/spawner.py:_expand_all`). `uNN.pod.prefix-expanded` shows 7 expanded root paths per pod and no `{username}` left.
- **Bearer writes through the hub work:** 401 without a JWT, 201 with one, DELETE 200.
- **Isolation between participants:**
  - u01's session on `/user/u02/{lab,stac/,oidc/}` → 403.
  - u01's hub API token on `/user/u02/stac/collections` → 403.
  - A u01-minted `stac:write` JWT → POST to u02's stac → 401.
- **The browser apps work under the two-level prefix,** in headless Chromium:
  - STAC Browser loads the catalog.
  - "Log in" goes to `/user/u01/oidc/authorize` with `redirect_uri=http://hub.spike.local:18080/user/u01/browser/auth` and PKCE S256.
  - The mock-oidc login returns to `/browser/auth`, `POST …/oidc/token` → 200, and "Log out" shows.
  - Later GETs on `/stac` carry Bearer and the session cookie, and get 200.
  - stac-manager logs in with `redirect_uri=…/user/u01/manager/collections` and creates a collection through its UI. The trailing-slash 307 keeps the prefix (`307 /user/u01/stac/collections/ → …/user/u01/stac/collections`, then 201). Delete is done through the API, because the stac-manager Delete button is an upstream no-op.
  - STAC Browser's `OPTIONS /stac` permission probe gets 405 from stac-fastapi, the same known noise as in `browser-apps.md`.
  - Chromium had to be told to treat `http://hub.spike.local:18080` as secure, since PKCE needs `crypto.subtle`. This only works with `channel="chromium"`; the default headless shell ignores the flag. On labs, the hub is https.
- **The hub keeps Jupyter's XSRF protection without breaking the apps.**
  - JupyterHub 5 checks XSRF on cookie-authenticated non-navigation requests. jupyter-server-proxy's no-op `check_xsrf_cookie` survives JupyterHub's patch; upstream names jsp in the comment (`jupyterhub/services/auth.py:_patch_xsrf`). So same-origin `fetch` from STAC Browser and stac-manager works.
  - A Lab upload with the `_xsrf` cookie as `X-XSRFToken` works (2 MB PUT → 201).
- **The `token=` pagination cursor works.** JupyterHub 5 ignores `?token=` by default (`JUPYTERHUB_ALLOW_TOKEN_IN_URL` defaults to false, `services/auth.py:370`). So `/stac/search?token=next:…` page 2 → 200, with 10 new items. This is the clash that cost the own chart 7 FAILs. For browser sessions it does not exist here; laptop access is the trade-off (finding 1).
- **NetworkPolicy: z2jh's default singleuser policy blocks stack-to-stack traffic on kindnet.** A/B tested:
  - With the policy, all 9 ports (5432, 8080–8086, 8888) on u01's pod IP time out from u02's Lab.
  - With it deleted, `:8888` is open and the 8 backends are refused, because they bind loopback.
  - `helm upgrade` restores it.
  - Controls: u02 → its own `127.0.0.1` finds all 9 open. The ingress controller pod cannot reach a user pod (only the hub's proxy may). u02's Lab reaches `hub:8081` (200).
  - Egress is also restricted (`privateIPs: false`). That is stricter than the own chart, which has an ingress-only policy, so its Lab terminal can reach other namespaces.
  - Labs runs Calico; re-run the probe there.
- **No cluster-scoped objects.** Our render has only namespaced kinds. The chart's defaults would render a ClusterRole and ClusterRoleBinding (userScheduler), plus 3 PriorityClasses with `podPriority` on. `values.yaml` turns off userScheduler, podPriority and userPlaceholder.
- **Participant pods are not Helm's.** `helm upgrade` leaves their UIDs unchanged. So does `kubectl rollout restart deploy/hub`, and the HTTP checks after it ran through the new hub pod. Singleuser changes apply only at the next spawn. That is safer on event day than the own chart, where a pod-template change restarts every stack at once.
- **Per-pod DB password.** A 10-line `modify_pod_hook` replaces the placeholder `generated-per-pod` with `secrets.token_urlsafe(24)` in all 6 DB clients of the pod. u01 and u02 differ.
- **Same pod as the own chart:**
  - 9/9 ready, 0 restarts.
  - The DB starts 6–8 s before the Lab.
  - `automountServiceAccountToken: false` (the KubeSpawner default without a service account).
  - Footprint requests on all 9 containers.
  - The notebooks match `docs/` (sha `30dd11287eb8`).
  - Scheduled → Ready in 7–10 s, images preloaded.
- **Memory** (`crictl stats` working set, during the run-2 checks): hub 148 MiB + proxy 24 MiB = **172 MiB** for the whole hub. The plan's estimate was ~0.5 GiB. Participant pods: 732 and 718 MiB (own chart: ~705).

## What z2jh gives for free, what it adds, what the cluster admin must grant

**For free:**
- One URL with username + password, and a login page.
- Per-user OAuth between the hub and each server.
- Proper cross-user denial (403).
- An ingress- and egress-restricting singleuser NetworkPolicy.
- A pre-puller that also covers `extraContainers` images.
- An admin UI and REST API to start, stop and restart one participant.
- Optional idle culling.
- Hub restarts and config changes don't touch running participants.
- Optional per-user home PVCs (`singleuser.storage.type: dynamic`), the fix for the "files lost on Lab restart" finding in `frontdoor-own.md`. Not enabled or tested here.
- The `?token=` pagination clash disappears for browser sessions.

**Extra moving parts:**
- **Hub and proxy.** The hub's sqlite needs a PVC (`hub-db-dir`), and with it a StorageClass.
- **The continuous pre-puller DaemonSet.**
- **The pre-puller hook Job**, which `helm install --wait` waits on.
- **A custom singleuser image** with `jupyterhub` matching the hub's version. Hub upgrades must bump it.
- **A pre-spawn step** run the day before. There is no "one Deployment per participant".
- **Two-level prefixes in every root path,** with `{username}` templating, and literal braces doubled because KubeSpawner calls `str.format` (finding 3).
- **A Bearer JWT is first tried as a hub token.**
  - In 10 minutes the hub logged 10 failed `/hub/api/user` lookups, fewer than the Bearer requests sent, so there is some caching. I did not confirm the cache in source.
  - No latency difference was measurable: 15 vs 15 ms per GET, 20 each.
  - The mock-oidc JWT does reach the hub API inside the cluster.
- **Credential lifecycle in our script:**
  - `deploy.sh` creates the Secret once.
  - Rotating means deleting it.
  - The participant list lives in both `allowed_users` and `deploy.sh`.

**Cluster admin needs** (labs, namespace `eoapi-workshop` only):
- Nothing cluster-scoped, with the values above.
- An IngressClass `nginx`, and one DNS name + TLS cert for a **single** host (`hub.<base>`), instead of one per participant.
- A StorageClass for the hub PVC (and for user PVCs if homes persist).
- Confirmation that Calico enforces NetworkPolicy, ingress and egress: re-run `netpol.*`.
- Pod Security: nothing privileged, since `cloudMetadata.blockWithIptables: false` drops the NET_ADMIN init container. The egress policy already denies `169.254.169.254`, but only if Calico enforces it.
- Capacity is the same as the own chart, plus ~0.2 GiB.

## Findings

1. **Laptop access to `/stac` does not work with a hub token (the 1 FAIL).**
   - The hub accepts the token, then jupyter-server-proxy forwards the same `Authorization` header, and stac-auth-proxy 401s anything that is not a valid JWT: `Authorization: token` → 401, `Authorization: Bearer <hub token>` → 401.
   - `?token=` is ignored by JupyterHub 5 → 302 to login.
   - `/raster` and `/vector` work with `Authorization: token <hub token>` (200), so QGIS-style tile or feature access is possible.
   - A fix would be `JUPYTERHUB_ALLOW_TOKEN_IN_URL=1` on the singleuser env. That brings back the own chart's `?token=` clash, and is **untested**.
   - The own chart has the mirror trade-off: laptop `?token=` works, but clashes with pagination.
2. **The pre-puller sets no `imagePullPolicy`** (`templates/image-puller/_helpers-daemonset.tpl`). A `:latest` image therefore defaults to `Always`, and a kind-loaded local image cannot be pulled. Fixed by tagging local images `:spike`. On labs, use versioned tags anyway.
3. **KubeSpawner renders every string with `str.format`.** The JSON env values (`PRIVATE_ENDPOINTS`, `SB_authConfig`, filter kwargs) need doubled braces; an unescaped `{` fails the spawn. Done in `values.yaml`, with a comment there.
4. **`modify_pod_hook` sees the env of init/extra containers as plain dicts**, but the Lab's as `V1EnvVar`. The first deploy's spawns failed (`'dict' object has no attribute 'value'`), and the hook now handles both. Deploy log 1 has the traceback.
5. **API paths under `/user/uNN/` answer 403 until a page under it has run the OAuth hop.** For example, `/api/status` right after `/hub/login`. That is normal for browsers (the Lab page does the hop), but scripts must GET `/user/uNN/` first.
6. **Lab files do not survive a Lab container restart**, as in the own chart (`storage.type: none`). z2jh's `storage.type: dynamic` is a one-line switch to a PVC per user. It needs a StorageClass and is not tested here.
7. **kind reloads both images (≈8 GB) on every `deploy.sh`.** Docker Desktop's image IDs don't match what kind compares. This is only local slowness.

## Reproduce

```bash
# prereq: kind cluster eoapi-spike (spike/kind/cluster.yaml) with ingress-nginx; images eoapi-spike-lab, eoapi-spike-db
spike/hub/deploy.sh            # build+tag+kind load, Secret once, helm upgrade --install (z2jh 4.4.2), pre-spawn u01,u02
spike/checks/frontdoor-hub/run.sh   # PASS|FAIL|BLOCKED lines; deletes+restores the singleuser NetworkPolicy, restarts the hub
python3 spike/checks/frontdoor-own/loc.py hub
```

Browser URL: `http://hub.spike.local:18080/hub/login`. Add `127.0.0.1 hub.spike.local` to `/etc/hosts`. Get a password with `kubectl --kubeconfig spike/.kind-kubeconfig --context kind-eoapi-spike -n spike-hub get secret participant-passwords -o jsonpath='{.data.u01}' | base64 -d`.
